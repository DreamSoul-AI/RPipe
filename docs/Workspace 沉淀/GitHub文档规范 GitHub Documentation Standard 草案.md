# GitHub 文档规范

状态：项目沉淀草案，待审阅。整理日期：2026年11月5日。适用于以 GitHub 为主要阅读入口的 README 和仓库 Markdown，供后续 workspace 汇集与规范修订参考。本文尚未成为 workspace 共用规范，也不改变飞书文档规范。

目标是让读者快速找到用途、操作、设计和依据，同时让 Markdown 源码便于维护。以下“应”表示本草案建议采用的基本要求，“建议”允许按文档规模裁剪。平台能力来自 GitHub 官方说明，文档分工与阅读取舍是本项目提出的编辑约定。

## 与飞书规范的适配关系

以[飞书文档规范](https://dreamsoul.feishu.cn/docx/DdmxdrNvBo9AMXxkAYmc4EJ6nwe)为参照，保留准确表达、事实依据、混排、段落减负和引用保全原则，调整依赖展示平台的条目。本次已读本地完整正文，未核实飞书云端版本一致性。

| 项目 | 飞书现有约定 | GitHub 建议适配 |
| --- | --- | --- |
| 页面标题 | 文件标题独立于正文，正文章节从 H1 开始 | 文件内保留一个 H1 页面标题，正文从 H2 开始 |
| 章节命名 | 优先中文层级序号 | 默认用简短主题标题，按 H2/H3 表达层级 |
| 空行 | 标题后不插空行 | 标题、段落、列表、表格和代码围栏之间保留空行 |
| 表头 | 显式加粗 | 使用普通 Markdown 表头即可，必要强调只用于具体内容 |
| 文档引用 | 原生引用及完整分享链接 | 仓内相对路径，外部完整 URL，避免个人机器绝对路径 |
| 块公式 | 源码要求单物理行 | 允许独立行的 `$$` 包围多行 LaTeX |
| Mermaid | 原生文本绘图组件 | 使用标注 `mermaid` 的代码围栏 |
| 图片 | 按飞书图片与导出限制处理 | 使用仓库相对资源，保留替代文字和可编辑源，按目标页面核显示 |

GitHub 的表格、数学表达式和 Mermaid 写法有各自平台支持，不能从飞书导入规则推定。[表格说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-tables)、[公式说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)、[图示说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)。

## 内容分工与阅读顺序

先确定文档回答的问题，再决定章节和篇幅。文件数量、章节数量和行数不是完成标准。

| 位置 | 主要内容 | 详细内容的去向 |
| --- | --- | --- |
| README | 项目用途、适用对象、当前能力、首次使用、目录与导航 | 完整操作进入使用指南，批次历史进入日期记录 |
| 使用指南 | 前置条件、完整步骤、预期结果、常用调整和必要限制 | 设计理由引用设计，历史验证引用运行记录 |
| 架构设计 | 系统职责、流程、质量目标、关键取舍 | 代码映射引用代码结构设计，演进引用开发记录 |
| 代码结构设计 | 目录、模块、接口、状态和允许依赖 | 实施步骤进入开发计划 |
| 开发计划／缺陷记录 | 当前任务、依赖、验收／活动问题 | 已关闭经过归日期记录 |
| 通用调研／文献调研 | 工程机制与方案／学术方法与证据 | 互相引用，保留阅读范围和来源 |
| 研究计划 | 问题、假设、对照、协议、资源和停止条件 | 实际执行进入运行记录 |
| 开发／运行记录 | 调整与决定／实际环境、命令、结果和限制 | 大日志、数据、checkpoint 放明确的外部证据根 |
| AGENTS.md | 研发行为、资料入口和项目专有约定 | 不重复整个命令手册、目录树或迭代进度 |

这些是编辑职责，不要求所有仓库拥有相同文件清单。适用的必备成果以项目研发约定为准。小项目优先在现有文档内分节，避免一节一文件；已有完整设计不为排版拆成分册。读取步骤与内部研发准入步骤分别组织，普通使用者不必先读完全部历史记录。

README 开头应能回答“是什么、能做什么、从哪里开始”。实际条件会决定能否运行时，将其放在对应操作前，不把所有限制挤到开篇。当前能力、已发布包和开发分支的差异应明确，完整 SHA、逐项 CI 与历史数字通过记录追溯。

## 文件名与页面标题

- 沿用项目已采用的命名方式，不仅为了美化批量改名
- README 保留惯用文件名，专项文档名称说明用途与对象；中英文命名是否必需由项目决定
- H1 使用准确的文档标题，正文不再重复同义大标题
- 草案、审阅状态和适用版本写在开篇元信息中，避免反复改文件名导致链接失效；法律、标准或明确发布版等需版本区分的文件按实际用途保留版本
- 日期记录保留日期和主题，历史名称、提交及运行身份不因排版改写

## 标题与导航

一篇一个 H1，主要章节使用 H2，子主题使用 H3。按真实从属关系使用 H4，不跳级，也不将 H3 机械设为上限。这个层级方案是本草案的编辑选择，GitHub 支持 H1–H6，并提供基于标题的文件大纲。[标题与大纲](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#headings)。

标题默认用主题名称，例如“安装”“数据与输出”“资源限制”。有真实顺序的操作放编号列表，通常不把“一、”“（一）”“1.1”叠加到所有标题。稳定的需求或协议编号可以保留，编号用于追踪而不是装饰。

较长或经常从中间查阅的文档，开头放少量主章节链接；短文可直接使用 GitHub 文件大纲。导航只维护主要入口，不重复展开每一个子标题。

章节链接使用实际生成的锚点。移动、改名或修改标题后检查入站引用，必要时保留稳定自定义锚点或旧入口，并明确新位置。不要凭中文标题想象锚点，不制造只在某个本地编辑器能打开的链接。GitHub 官方区分[章节链接与自定义锚点](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#section-links)。

## 段落、混排与强调

每段围绕一个中心问题，先给结论或动作，再给条件和理由。发现长段时先按职责拆分，不靠加粗、分号或表格掩盖信息拥挤。不设置统一字数或行数上限。

中文与英文词、缩写之间通常加空格，代码标识使用行内代码，例如 `run_root`、`config.yaml`。标点保留自然语义，文件名、URL 和代码内的字符不机械改写。

不同段落之间保留一个空行，不依靠源码软换行分段。标题、列表、表格及代码块前后保留空行。嵌套操作中的代码块缩进到所属列表项，确认渲染后仍属于该步骤。

加粗用于少量关键概念或会影响决定的条件，不把整段、所有链接或每个表格单元格加粗。删除对话开场、情绪化评价和无依据宣传。日期记录仍须保留决定来源、失败与必要经过，不能以删除“过程痕迹”为由丢失证据。

## 列表、表格与提示

操作顺序用编号列表，并列信息用无序列表。一个步骤有多个动作时，先判断是否应拆开。检查任务可用任务列表，但勾选状态须与实际证据一致。

表格用于短而可比较的内容，例如接口参数、职责、状态和方案差异。单元格出现多段解释、完整命令或长限制时改为小节，避免读者横向滚动才能理解主要内容。没有固定列数限制，以窄窗口可读为判断依据。

提示应紧邻受影响的动作。普通说明使用正文；会导致误用、数据损失或无效判断的条件才强调。可采用 GitHub 提示语法，但不能将必要条件折叠或只用颜色表达。[提示语法](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts)。

折叠块只放可跳读的补充、完整输出或旧链接说明，核心操作和阻断条件保持展开。默认使用标准 Markdown，只有折叠等实际需要时采用少量 GitHub 支持的 HTML，不依赖自定义 CSS、脚本或页面主题才能读懂。

## 命令与代码示例

- 代码围栏注明语言，例如 `powershell`、`bash`、`python`、`yaml`，纯输出用 `text`
- 说明工作目录、前置环境和必要输入；不同 shell 的命令分别标明，不把 PowerShell 当作所有平台通用命令
- 占位符与可直接执行的值区分，执行前说明应替换哪些内容
- 安装、下载、训练、清理和发布等副作用在对应命令前说明，不能把查看命令和真实执行混成一段
- 完整示例展示必要文件及它们的关系，避免读者猜省略部分；多个页面引用同一示例，避免分别维护不同副本
- 区分实际运行输出、示意输出和预期结果，不编造通过状态；搬移示例后核对原内容、路径和消费者
- 不在示例中写凭据或用户私有路径；确需记录实际机器路径时放在对应执行记录并核可见范围

## 链接、来源与资源

仓库文件和图片使用相对路径，便于随分支、fork 和 checkout 阅读。路径含空格时使用明确的 Markdown 链接语法，检查大小写及 URI 编码，不能只以 Windows 本地可打开判断有效。[相对链接](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#relative-links)。

当前使用入口链接当前文件；支持历史结论的源码和结果固定到实际提交或归档身份。来源链接放在支撑结论附近，说明实际阅读与验证范围。PR、Issue 和 CI 可作为依据，但项目结论与后续步骤须在 Markdown 中可读。

公开仓库引用飞书内部链接时注明访问条件，不为方便阅读扩大权限。引用到飞书时重新核对对应资源和可访问性，不能把仓内相对链接机械替换成同名云端文件。

## 公式、图示与图片

行内公式用 `$...$`；公式含下划线等与 Markdown 冲突的字符时，采用美元符号与反引号共同包围的行内写法，避免被解析为强调。较长公式可用独立行的 `$$` 包围，推导保持可读的多行源码，不继承飞书单物理行限制。公式附近解释符号、单位和适用条件，避免用截图替代可编辑数学内容。GitHub 支持相应数学表达式语法，其他预览器可能不同。[数学表达式](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)。

流程与架构图优先保留 Mermaid 围栏源，文字说明应让读者在图未渲染时仍理解主要关系。科学曲线保留实际生成数据、方法和必要导出，不用示意图冒充测量。图片提供有意义的替代文字，说明来源和单位；PNG 或 SVG 等按目标显示与导出效果选用，不沿用飞书的统一禁传 SVG 条款。Mermaid 语法须按 GitHub 实际支持版本核验。[Mermaid 支持](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams#creating-mermaid-diagrams)。

转换到飞书时按其原生图、公式及图片要求适配，保留原始语义和可编辑源。GitHub 解析成功不代表飞书页面或导出正常，反向同理。

## 文档模板

以下是可裁剪的起点，不要求每个文件填满所有章节。示例中的占位说明应替换为真实内容，未形成的结果标为未验证，不保留空壳。

### README

```markdown
# 项目名称

一句话说明用途和适用对象。

当前能力和发布状态，提供首次使用入口。

## 开始使用

前置条件、最小操作及预期结果。完整步骤较长时链接使用指南。

## 设计与目录

核心职责和实际目录入口。

## 文档导航

按使用、设计、计划和记录提供少量链接。

## 参与开发

研发约定、测试入口和协作流程。

## 许可

实际许可证与第三方来源。
```

### 使用或设计文档

```markdown
# 文档标题

说明本文回答的问题、适用条件及当前状态。

## 总览

使用文档写操作结果与准备条件，设计文档写职责与质量目标。

## 主要内容

按任务或职责组织小节，必要时提供代码、图和简短对照。

## 边界与取舍

仅说明影响使用或设计决定的条件及理由。

## 相关资料

链接详细协议、实施计划、直接来源与验证记录。
```

### 计划或日期记录

```markdown
# 计划或记录主题

计划说明当前目标与范围，记录注明实际日期、版本和环境。

## 当前结论

计划写待办与决定，记录写实际完成和未完成。

## 工作与依据

计划写依赖、步骤和验收；记录写真实调整或执行及证据位置。

## 下一步

写可执行动作、停止条件或需校准的具体事项。
```

开发计划与研究计划仍须独立，具体结构由工程任务或研究问题决定。模板不替代研究中的数据、模型、算法、指标、对照和判读设计。

## 交付检查与迁移

1. 从读者目标走读开篇、一个完整操作、解释密集处和图表前后，核对是否找得到下一步
2. 核对事实、代码／配置、来源与版本，区分已实现、已验证、已发布和待办
3. 检查文件链接、章节锚点、图片及移动后的入站引用，必要时保留旧入口
4. 通过 Markdown 解析检查标题、表格、列表、代码围栏和强调；含公式、Mermaid 或复杂嵌套时另看实际目标预览
5. 检查 Git diff、编码和意外删除，区分解析检查、浏览器视觉检查与真实命令验证，不将一种通过冒充另一种

不为纯文案改动新增无意义的代码测试，不默认新增工作流、文档站点或工具依赖。格式化、预览和链接工具按现有环境选用。

迁移按实际阅读问题逐份进行：先入口，再当前使用、设计与计划，最后按需要处理历史记录。已有编号、引用和内容完整性先核再改，不批量删标题序号或重命名文件。GitHub 与飞书尽量共用内容，导出时做平台适配；双端均可编辑时须保留同步基线并处理冲突，不能假定任一端永远覆盖另一端。
