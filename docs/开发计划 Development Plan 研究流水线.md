## （二）DP4 的验收与实施顺序

1. 先写受控回归：首个Run运行期间中断，后续Run未启动；开始前即取消时零执行；已有成功result字节不变，不能因返回空元组或成功前缀而退出0
2. 首次中断进入取消合同；重复中断按明确、有界的升级策略处理，仍只操作本次资源。已确认取消且清理完成拟返回130，清理失败或unknown返回非零并保留真实状态，不将未知重写为cancelled
3. 成功、准入错误、取消和清理失败后均恢复原信号处理器。保持主线程信号约束，不能覆盖嵌入调用方的长期处理器；read/plan等只读入口保持原行为
4. 用既有CPU子进程fixture验证源输入不变、peer和无关进程存活、owner在确认收尾后释放、首次异常与清理异常分列；Windows扩展导致的未知后代不扩大成硬停止承诺
5. 先跑受影响CLI/API/执行回归，再按真实修改范围跑有界CPU与既有CI。实际需要改启动/安装路径时再做对应制品验证，不为纯入口改动重写数学算法或调整研究门
6. 实施完成才同步README/架构的能力状态、缺陷和日期记录。当前计划不表示上述代码、退出码约定或回归已实现，也不授权GPU或E3/E4运行

DP4之后先核研究准入与所缺证据，再按实际反例决定是否还有代码问题。显存硬限、自动GPU分配、集群调度与大包拆分没有当前需求依据，不列为顺手新增。DP5待候选版本及发布范围明确后推进。
