# Workspace 经验建议

[返回文档导航](../README.md)

2026年11月26日。接收方：DreamSoul-AI/workspace。以下做法已在 RPipe dev 实际采用，共用模板如何吸收由 workspace 核对现有规则后决定。经验稿和导航按用户授权经 PR 交付，main 同步沿正常 dev → main 流程，不创建新版本或改动既有发布附件。

## CI 按影响验证与证据复用

**优先减少不相关检查和重复执行**，保留必要验证及真实失败语义。RPipe 原先在 PR 和合入 dev 后各执行一轮完整检查，纯文档也安装业务依赖、运行 CPU 与打包。此次主要收益来自按影响选择及合并后复用，并非完整回归本身明显变快。

### 可复用的做法

| 问题 | 做法 | 适用条件 |
| --- | --- | --- |
| 文档、配置、代码都跑同一大矩阵 | 先核对实际消费者，再选择文档、受影响行为或完整回归；已证明集合相同的批次可合并收集与启动 | 文件后缀只是线索。Markdown 若参与构建、生成或协议输入，仍须验证消费者；未知范围及共享合同按项目规则扩大检查 |
| 合并后重复验证已通过内容 | 将成功回执绑定受测内容、目标基线、验证范围和运行身份，合并后先核验再决定是否复用 | 不能只看同一分支、相同 PR 或绿色状态；必要输入和环境前提仍须适用。条件不成立时执行所需检查 |
| 减少任务后，必需检查消失或意外跳过变绿 | 保留必需汇总门，由它核对计划及被选任务结果，明确区分合法未选与执行失败 | 工作流触发、汇总名称与真实保护规则对应；失败、取消、意外跳过或缺失结果仍阻断合并 |

RPipe 的复用同时核对仓库、已合并 PR、最新对应成功运行、head、before／base、文件树、选择指纹、run ID 与重跑编号。测试合并提交和实际合并提交可以 SHA 不同，但文件树与基线必须匹配，回执保留原受测提交。CPU 与打包各自核验，不能用其中一项的成功代替另一项。

直接 push、新基线、缺失／过期回执或 API 不可用时，RPipe 恢复完整检查；最新失败不能改用旧成功。原始输入、外部依赖、运行环境或验证阈值变化的项目，还应判断旧证据是否适用，不能仅凭 Git 文件树宣称这些条件相同。

### 实际结果与证据

| 场景 | 本次并行整轮耗时 | 已核验内容 |
| --- | --- | --- |
| 完整代码 PR | 13分26秒 | 四组跨平台 CPU、真实 TensorBoard 读回、两平台严格 wheel／sdist 安装与来源检查 |
| 代码合入 dev | 21秒 | 分别引用该 PR 的 CPU／打包回执，基线和文件树匹配，重任务未重跑 |
| 纯文档 PR | 最终候选24秒，前一候选28秒 | 只做标准库文档检查与汇总，不安装 PyTorch、不执行打包 |
| 文档合入 dev | 31秒 | 引用文档 PR 自身的成功回执，重任务未执行 |

耗时口径为工作流 created_at 到 updated_at，CPU 与打包并行取整轮跨度，不将两者相加。完整代码 PR 与其 dev 检查合计13分47秒，不含人工核验与合并间隔。旧约27分钟来自不同候选和环境，只作历史参照，不据此宣称同条件性能提升比例，也不承诺其他项目达到相同秒数。

真实失败路径也已验证：文档 PR 临时加入明确标注的失效引用，两个必需汇总门失败，PR 在非 Draft 状态下仍为 BLOCKED。随后修复引用，新候选通过；未靠取消失败、跳过必需任务或调整保护取得通过。本地反例、失败原件及不同候选的成功结果分别保留。

### 给 workspace 的具体建议

共用研发入口已有按影响验证、保留证据和读取项目约定的要求，建议先合并已有内容，重点补清“检查选择在运行前完成，复用需要可核验依据，必需检查仍能明确上报”。详细机制与可选示例归 CI/CD 教程，项目矩阵、分支名、预算和包验证合同留在 REPO.md 或项目测试说明，不把 RPipe 的四组／两组矩阵或回执 schema 写成全项目固定标准。

采用前可按四步核对：1) 查真实触发、Rulesets 与步骤耗时，区分安装、测试、打包及重复执行；2) 按消费者定义影响范围、完整回归条件和证据复用条件；3) 本地验证后跑一次真实 PR，再核对合并后的计划、回执和任务状态，同时验证受控失败确实阻断；4) 用固定候选及统一口径记录结果，再决定是否推广。无需为测速度反复触发远端或通过缩小业务数据、放宽断言获得提速。

本轮也确认了一个平台前提：配置 `workflow_dispatch` 不等于手动入口立即可用，[GitHub 要求默认分支具有相应入口](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。本案例最初的 dev 验收阶段没有更新 main，因此当时只记录手动规则已定义。后续默认分支采用须核对真实入口，不能回签为旧轮次已验证手动触发。

本次按用户要求交给 workspace 维护者，作为现有 Actions 策略建议的已验证案例。接收、去重、issue、模板修改及正式采用状态分别记录，不将“已交接”写成“已发布”或“其他项目已同步”。
