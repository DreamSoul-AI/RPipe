# 四、失败定位与环境前提

## （一）NumPy 原生退出

两项科学 worker 无输出并以 `3228369022`（`0xC06D007E`）退出。独立于 RPipe 的 import numpy 即复现，numpy→torch 仅输出 before numpy，尚未执行到 Torch；因此早期“Torch worker 导入失败”的宽泛判断被进一步定位，不能把根因归给 Torch。

faulthandler 指向 NumPy __init__.py 第 881 行 blas_fpe_check 的 20×20 矩阵乘法。只观察的 Windows 异常处理器取得 DelayLoadInfo：dll 为 libiomp5md.dll、last_error 为 126，结构大小与 x64 预期一致；NumPy 构建配置使用 mkl-sdl / MKL 2025。限定解释器根和 Library/bin 未找到该 DLL，Torch/lib 中已有副本，SHA256 为 `eb14cf741b10a6ca176acded284bff7b069e421f49927e28fef9685c6f62abf3`。当前 PATH 有 Library/bin，但没有 Torch/lib。

仅在诊断子进程 PATH 前置该 Torch/lib 后，NumPy 单独导入及 NumPy→Torch 均退出 0、stderr 为空；最终测试采用相同临时前提并继承到 worker。证据在 environment-diagnosis/reproduction.json、numpy-delayload.json、diagnosis-summary.json、torch-path-comparison.json 及对应 stdout/stderr。没有复制 DLL、使用 KMP 忽略开关或修改持久环境。全局环境仍未修复；未来科学测试需使用可正常加载 OpenMP 的受控环境，此次对照不外推到其它版本组合。
